# 技术决策记录

## 2026-11-27 Android 聊天时间分段

用户按下发送时，手机持久保存本次请求的时间。普通回复、定时消息和已办事项回执以服务器完成该条回复的时间为准；断线重试及离线补收沿用已保存的时间。Android 按手机时区显示日期，同日以相邻两条消息间隔满五分钟为界，跨日优先显示完整日期。分页从上一页最后一条消息接续。旧记录缺少可靠时间时保留原文。

## 正式与测试环境各绑定一个 Android 安装

第一个通过当前版本检查的安装主动连接时，SQLite 用唯一行原子占位。之后每个手机业务请求都核对安装标识及会话，第二个安装返回 HTTP 403。首次下载与应用更新仍然公开。绑定和拒绝日志只记短指纹，手机无需登录，网页定时任务也无需选择设备。消息、记忆和经期继续沿用升级前的会话编号。断线或换网络不会自动腾出名额。

## 定时任务由服务端触发，消息按手机收取

管理员设置北京时间的五段 Cron 表达式和生成指令，服务端自动投给本环境绑定的安装。每个触发时刻有独立执行编号，沿用正常聊天的生成、归档和上下文压缩通路。进入对话的只有 Piggy 的最终回复。主动轮次可以读取历史和记忆；经期和记忆的修改仍需要用户亲自提出。

服务端保存最终回复。Android 进程和系统周期作业共用收件箱游标，只有成功写入的新消息才会发布本机通知。通知采用普通聊天回复的正文预览，并在聊天页可见时静默。

## 正式与测试各部署一整套 Piggy

**原因。** 软件仍在快速迭代，测试手机需要频繁验证新版，日常使用的手机需要稳定。同时，Go 网关按本环境的最新 `versionCode` 接受手机请求；只分开 APK 下载地址，仍会让旧版手机被共享网关拦住。

**选择与后果。** 两个 Android 包名允许同机安装。每个包连接固定的 HTTPS 入口，后面各有 Go 网关、Pi、管理凭据、SQLite、附件目录和更新清单。这样可以在测试环境独立改协议、改模型、试数据库迁移，最后再决定何时正式发布。两套部署共用一台 CVM；当前也共用 OpenAI 密钥，所以主机故障和上游配额仍是共同边界。实现见 [Android 构建配置](../android/app/build.gradle)和[服务构建脚本](../server/admin/build-release.sh)。

人格调整默认先在测试版验证，再按发布安排同步正式版。验收时同时核对提示词模板和 Pi 进程实际加载的 `PIGGY_COMPANION_NAME`。这个字段按环境配置，两边部署同一份代码也可能生成不同的身份描述。

## 手机发起对话，服务端持有 Agent

**原因。** 模型、工具和用量需要集中管理；手机操作要简单。**选择与后果。** Android 通过固定地址免登录发消息，Go 网关转给 Pi，OpenAI 密钥由服务端持有。网页版须登录，可以看历史、Agent 能力和调整模型设置。对话维持单向写入，网页不续聊，因此手机无需同步来自网页的新消息。网页保存的模型配置作用于本环境的下一次请求。实现见 [Go 网关](../server/admin/main.go)和 [Pi 服务](../server/server.ts)。

## 聊天原文与模型上下文分别保存

**原因。** 网页要保留用户实际看到的问答；压缩模型输入时，这份历史仍然有用。**选择与后果。** SQLite 的 `turns` 保存原文与状态，`active_context` 按会话顺序保存工作上下文；成功结束一轮时一并提交。Android 正式版 0.17.0（测试版 53）起，设备以 SQLite 保存收到的完整轮次，桌面管理记录与模型上下文各自独立。聊天列表按 24 轮一页读取，最多缓存三页数据，只为可见区域创建消息视图。旧版本已从设备淘汰的记录不会随升级回填。模型输入读取工作上下文，用模型回报值校准本地估算，正式版上限为 300,000 个输入 token，测试版为 30,000，方便用较短对话验证压缩。早期开发阶段允许旧会话恢复时缺少工作上下文，这个容忍范围不构成今后正式数据迁移的承诺。实现见 [Journal](../server/journal.ts)和 [Pi 服务](../server/server.ts)。

## 按模型实测用量校准，异步压缩工作上下文

普通消息、附件和工具续轮直接调用模型。服务端计入上次实际输入的缓存部分，在同模型、同一摘要版本的基线上估算新增内容。新会话、缺少可用实测值或摘要刚替换时，圆环使用本地估算，下次模型回复后校准。附件首次进入上下文的用量尤其依赖这次校准。

80% 是后台压缩触发线。一次回复可以越过目标窗口，模型自身的输入限制仍然适用。每个会话同时最多生成一份摘要，只处理已经入库的历史，通常保留最近三轮。摘要可用后单独用 SQLite 事务替换快照的旧前缀；生成中的回复继续使用自己的快照，期间新增的轮次照常追加。摘要失败留待后续检测重试。聊天原文、附件保留期、人格、技能和工具的加载逻辑均独立于摘要。实现见[上下文压缩](../server/compaction.ts)。

## 长期记忆由用户明确发起

用户明确要求保存或更正时，模型依据原话拆出可以独立变化的事实，保留人物、条件、否定和时间。每条事实关联摘录和来源聊天轮次。服务端按事实正文检索已有候选，明确更正时更新同一条，允许同时成立的事实分别保存。修改在同一个 SQLite 事务中提交。实现见[记忆存储](../server/memory-store.ts)和[证据提取与匹配](../server/memory-planner.ts)。

## 附件保留七天，文档在手机上排版

**原因。** 手机要能查看双方的附件，管理页要能下载；永久存原件会持续占用服务器磁盘。服务端转换 Office 文档还会增加传输往返和 CVM 负载。**选择与后果。** 上传件和模型生成件都以文件形式限期保存，数据库记录引用、名称和期限。到期清理原件，历史消息继续保留文件信息。Android 在 APK 中内置 LibreOfficeKit，已在手机上的文档首次预览也能离线打开；远端附件需要先下载。实现见[文件留存](../server/retention.ts)和[手机 Office 阅读器](../android/app/src/main/java/dev/pichat/OfficeReader.kt)。

上传件只在所属用户消息上引用。生成和工具续轮使用相同的文件引用。压缩移除原消息后，可按聊天关键词或文件名查找历史轮次，再通过 `read_chat_context` 重读该轮仍有效的原件。

## Android 本地草稿

输入时保存文字。点击发送会一并保存本条消息和重试编号，随即腾出输入框供用户写下一条。等待期间可以编辑下一条的文字、选择或移除本地附件。待发送消息与下一条草稿分别保存各自的附件列表，点击发送后才上传。回复成功后保留下一条草稿；失败时如果已经写了下一条，可单独处理上一条，两份内容都可跨进程重启恢复。

## 保留签名整包，更新时复用文档引擎

**原因。** 手机需要启动时强更以匹配本环境的接口，而一次普通界面改动无需重传几十 MB 的相同引擎。**选择与后果。** 发布器标记签名 APK 中的引擎区间。手机校验本地引擎匹配后，只下载该区间前后的两段，在本地还原安装包，检查大小、哈希、包名、版本和签名，再交给系统安装。引擎变化或增量失败时自动下载整包。进度条按本次网络下载量计算；手机需留出完整 APK 的临时空间。实现见[发布器](../server/admin/updates.go)和[安卓更新器](../android/app/src/main/java/dev/pichat/AppUpdater.kt)。

### 长期记忆的向量索引

每条事实正文在所属会话中独立建立向量索引。搜索最多返回 20 个候选，接受漏召回。正文变化后撤销旧文件映射并重建索引，索引未完成时告知调用方。来源核对可直接按轮次读取原始聊天。

迁移在 SQLite 事务中把有效主题成员转为带人物和关系的独立陈述，并保留最新证据及未导入的有效旧记录。主题、成员、分类字段和目录工具随迁移移除。已替换的索引文件和旧主题向量库通过持久队列清理。

## 回复文件与后台发送

用户上传的附件保留在原始消息上，供模型追问时使用。代码解释器查看图片产生的缩略图和工作副本也可能带有文件引用。服务端只归档最终回复明确链接到 `/mnt/data/deliverables/` 且 OpenAI 标注指向同一链接的成品。专用图片生成工具的输出继续作为生成图片交付。

Android 发送前在本地保存请求编号、内容与附件编号，从 Android 测试版 0.15.0-test.4 起，由系统 JobScheduler 调度上传与收取回复。Android 12 及以上优先使用加急任务，调度配额或省电限制可能延后执行。系统中断任务后用同一请求编号继续。等待阶段不发布系统通知；后台成功保存最终回复后，仅用正文发布一次提醒。聊天页面可以独立销毁和重建。手机断开后，服务端继续处理已受理的请求并记录结果。同一编号重连时，正在生成的请求返回等待提示，已经完成的请求返回原回复。短暂网络错误最多自动重试三次；已受理的请求另按三秒间隔查询。发送结束即停止前台服务。

## 后台发送的省电设置

Android 设置页按机型命名入口。vivo / iQOO 显示「后台耗电管理」，优先用电池组件公开的后台耗电管理 action 打开列表，用户选择当前安装的 Piggy 后再选「允许后台耗电」。此处采用维护者在 vivo S50 Pro mini（OriginOS 6）看到的菜单文字。公开固件样本可以核对列表入口，但不能证明每个版本都向第三方开放单应用详情。OPPO 显示「应用耗电管理」，由用户进入 Piggy 后开启后台活动。厂商入口不可用时先显示本机操作路径，用户可以选择继续前往系统电池设置。Android 通用入口继续打开本应用的电池页。

入口核对依据包括[公开 vivo 系统镜像中的电池组件声明](https://github.com/el-vertedero/iqoo_canoe_dump/tree/e73f73042dee4591810c3727bb2d7d84b233bd96/system/system/app/IqooPowerSaving)和 [ColorOS 14.1 使用手册的应用耗电管理说明](https://s3.eu-west-3.amazonaws.com/par-sow-cms-oppo-com/cms/userManual/manual/3524d044-8881-4c19-b61f-c2da2949c1f7/ColorOS%2014.1%20User%20Manual.pdf)。该 vivo 镜像来自其他设备；具体机型仍需真机核对。

## Android 经期日历

手机按当地日历日期计算预测。测试版使用当前安装的聊天会话编号同步专属日历，SQLite 的 cycle_calendars 保存实际日期和周期设置。手机私有偏好保存离线副本和有序待同步修改。旧版本地记录在首次打开日历或发送聊天时迁移，重试用序号去重。首次使用须主动记录开始日。后续实际记录重新锚定预测，已记录的两次开始日之间不会插入虚构的月经。起始日可以单独保存。未记录结束时按设定天数显示预计结束日。用户可在日历上记录、更正或撤销每次的实际最后一天（含当天），实际区间优先于预测。未来周期仍按设置估算。撤销起始日会同时移除对应结束日。不同安装的日历互相隔离。聊天中的 period-calendar Skill 引导 Agent 按需调用 read_cycle_calendar、record_period、update_period_record、cancel_period_record 和 update_cycle_settings。撤销前核对本轮读取的实际记录，按用户要求区分整次经期与仅结束日。更正开始日和结束日时一次写入，校验失败保留原记录。设置可单项调整。工具访问手机日历使用的同一份记录。

本版只对 21–35 天的周期显示排卵估算。排卵估在周期第「周期长度减 14」天，易孕窗取前五天至后一天，可与经期或黄体期重叠。此范围是产品显示策略。周期、经期长度可分别设置，出于记录目的可以使用更长或更短的周期。日历法无法确认排卵，预测不可作为避孕依据。[ACOG 对日历估算与易孕窗的说明](https://www.acog.org/womens-health/experts-and-stories/the-latest/trying-to-get-pregnant-heres-when-to-have-sex)

## 聊天等待短句

网页「Agent 能力」维护本环境的短句列表，保存在 SQLite。Android 前台约每小时同步，失败时沿用最近成功的列表，首次离线使用内置短句。仅等待正文时，每十秒轮换一句；上传、重连与正文使用各自的显示方式。短句仅供界面展示，不进入模型上下文和聊天记录。

## 工具写入、恢复与日历显示

聊天引发的日历和记忆写入与该轮操作回执在同一 SQLite 事务提交。生成回复中断或进程重启时，从回执告诉用户已成功的操作。相同工具、参数和错误在同一轮重复出现两次后，下一次模型请求关闭工具，要求给出可见答复。历史回复附件的引用随原始轮次保留，可以按文件名查找并在七天内重新读取。

新日历使用 30 天周期和 7 天预计经期，保留已有设置。月历用经期、卵泡期、排卵及黄体期标记日期，保留原有浅绿色区间及排卵日颜色。

## Android 回复附件的位置和保存

Pi 按最终回复中经上游标注核验的链接交付文件，并随文件记录说明在可见正文中的 UTF-16 结束偏移。手机按该位置插入图片或文件卡片。缺少位置时追加在正文后；旧版逐条编号且与附件一一对应的说明可按编号还原。长按图片或文件卡片显示操作菜单，预览页的图片长按和右上角按钮共用此菜单。保存原件到系统相册或下载目录中的 Piggy 文件夹。外部打开使用 Android 应用选择器，分享使用系统分享面板，并向选中的应用授予原件的临时只读权限。

## 专属表情库与聊天引用

网页「Agent 能力」维护两端共用的表情名称、使用场景和上架状态。每个环境的 SQLite 单独保存素材。内置表情包按版本一次性导入，手动编辑和上下架选择跨重启保留。替换内置包时，通过图片 ID 移出旧素材。被历史消息引用的图片仍可按原 ID 读取。

每轮给模型提供当前上架表情的 ID、名称和场景，由 `piggy-stickers` Skill 引导 `send_sticker` 工具选取至多一张。回复可带文字或只含表情。工具选择随该轮成功提交，同一消息编号重试返回同一引用。回复和手机记录只保存 `stickerId`，手机按需下载并缓存。图片内容使用稳定 ID，下架后仍可从旧聊天读取。附件的七天清理独立运行。

## 2026-11-25 聊天和工作共用一段对话

模式随每次手机发送一并提交。后台重试沿用发送时的模式，用户在等待期间可以为下一条切换模式。服务端按模式读取本环境的模型、思考强度和速度，按该模型估算用量并生成回复。两种模式共享对话编号、当前上下文、人格、工具和长期记忆。旧客户端和定时消息使用聊天模式。

## 2026-11-27 当地天气与七点提醒

从 Android 测试版 58 起，首次启动请求系统大致定位权限，后续沿用“仅在使用中允许”。拒绝后仍可聊天，之后可在系统应用权限中调整。版本 57 中明确关闭过天气的用户，在仍有系统授权时单独确认是否恢复使用。使用聊天页时更新。Android 测试版 59 起同时请求精确和大致前台定位，系统授权精确时使用和风支持的 0.01° 格点，只授权大致时沿用 0.1°。旧版已授权大致定位的用户升级后有一次选择精度的机会。权限降级后在下次同步时替换原格点。聊天或收件请求同步最近一次位置和采集时间，服务只保留一份，24 小时过期。关闭或撤销权限后，手机在下次成功同步时清除服务端坐标。天气工具将大致格点用于查询，模型读取地区名称和天气。用户点名城市时优先查询该地。

测试环境在网页「定时任务」登记普通 Cron 任务（默认北京时间 07:00），任务指令要求 Piggy 执行 `local-weather` Skill。调度器只提交指令，用户可编辑、暂停或删除；服务重启不会重建任务。手机的最近位置保存在 `weather_location`，不会拼进系统提示词。天气 Skill 负责定位、预报和来源，以北京时间解释日期。和风实现用 GeoAPI 反查市区，在回复开头说明位置；整天取逐日最低和最高温，具体时段取小时预报，官方预警单独查询。早间提醒的天气条件、时间范围和静默规则都由该任务指令维护。条件未满足时由任务调用 `skip_scheduled_message`，管理页记录「无需提醒」。手机沿用已有后台收件与通知，系统挂起时可能晚于七点收到。
